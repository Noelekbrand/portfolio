Overview

The goal was to replicate the kind of HIL workflow used in production automotive ECU development — where a software model is validated against a physical plant before any code is deployed to real hardware.

A Stateflow state machine models the window lift ECU logic. The Simulink model generates CAN frames over a virtual bus (MathWorks Virtual 1) using a DBC signal database, while a MATLAB System Object bridges the model to a physical Arduino Leonardo driving a real DC motor with an MDD3A motor driver.

A Python/pytest suite runs end-to-end tests via the MATLAB Engine API, and a GitHub Actions pipeline continuously validates the codebase on every push.

ECU state machine — Stateflow

The window lift ECU is implemented as a four-state Stateflow chart. This mirrors how real automotive ECUs are modeled in Model-Based Design workflows — the Stateflow chart becomes the authoritative behavioral spec for both simulation and code generation.

IDLE
→
MOVING_UP
⇄
MOVING_DOWN
→
OBSTACLE_STOP

State definitions

  • IDLE cmd = 0. motor_speed = 0, motor_dir = 0. Waiting for a valid command.
  • MOVING_UP cmd = 1. motor_speed = 200, motor_dir = 1. Position rising toward upper limit.
  • MOVING_DOWN cmd = 2. motor_speed = 200, motor_dir = 0. Position falling toward lower limit.
  • OBSTACLE_STOP obstacle = 1. motor_speed forced to 0. Safety state — remains until obstacle clears.

CAN bus communication

The ECU outputs are transmitted as CAN frames over MathWorks Virtual 1 using the Vehicle Network Toolbox. A DBC signal database defines both message frames, enabling any standard CAN tool (CANalyzer, cantools, Python) to decode the data without extra configuration.

System architecture

The full HIL loop: the Simulink model runs the ECU and CAN layers on the PC, while the HILSerialBridge System Object translates motor commands to serial ASCII and feeds encoder feedback back into the simulation.

Python / pytest test framework

Tests are driven via the MATLAB Engine API for Python, which allows pytest to trigger Simulink simulation runs and read back signal values. Each test case follows a polling pattern — checking signal stability rather than relying on fixed sleep durations — making the suite robust across machines.

test_window_lift.py — TC_OBSTACLE_STOP
def test_tc_obstacle_stop(fresh_simulation):
    """TC_OBSTACLE_STOP: obstacle=1 during upward movement → motor_speed stable at 0."""
    eng = fresh_simulation

    # setup: drive down to make room for upward movement
    set_cmd(eng, CMD_DOWN)
    wait_until_position_below(eng, threshold=30)

    # begin moving up
    set_cmd(eng, CMD_UP)
    time.sleep(1)

    # inject obstacle signal mid-movement
    set_obstacle(eng, 1)
    signals = wait_until_motor_stops(eng, timeout=10)
    set_obstacle(eng, 0)

    assert signals['motor_speed'] == 0, f"Expected motor_speed=0, got {signals['motor_speed']}"

Test coverage

  • TC_MOVE_DOWN motor_speed = 200, motor_dir = 0, position decreasing
  • TC_MOVE_UP motor_speed = 200, motor_dir = 1, position increasing
  • TC_OBSTACLE_STOP obstacle injection → motor_speed stable at 0 within 5 s

Engineering insights

Using a DBC file as the single source of truth for CAN signal definitions — rather than hardcoding offsets — made the test layer completely decoupled from the Simulink model. Any change to signal scaling or bit positions only requires updating one file, and the CI catches regressions immediately.

The HILSerialBridge is wrapped in coder.target('MATLAB') to prevent Simulink's code generation from attempting to compile the System Object — a common pitfall when mixing interpreted and generated code in the same model.

Polling rather than fixed sleeps in the test cases makes the suite portable across machines with different MATLAB simulation step sizes. This is the same principle used in production HIL frameworks where test timing must not be coupled to host CPU speed.

This architecture mirrors the Model-Based Design workflow at automotive OEMs: Stateflow for ECU behavioral modeling, CAN for signal exchange, and automated HIL regression testing to catch defects before any deployment to physical hardware.
